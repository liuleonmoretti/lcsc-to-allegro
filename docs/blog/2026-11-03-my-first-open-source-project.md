# 我的第一个开源项目：把立创封装带进 Allegro 16.6

日期：2026-11-03

项目：[lcsc-to-allegro](https://github.com/liuleonmoretti/lcsc-to-allegro)

这是我整理到 GitHub 的第一个开源项目，也是这个工具箱的第一篇项目记录。它解决一个具体问题：手里有立创 C 编号或 KiCad 封装，希望在 Cadence Allegro 16.6 里使用，如何减少重复建库，同时保留可以核对的转换过程。

## 我做了一个什么工具

LC2A 是 Windows 本地命令行程序。输入 C 编号或 `.kicad_mod`，在支持的几何范围内生成 Allegro 16.6 的 `.pad`、`.dra`、`.psm` 文件，并保留源数据、日志和验证记录。

这个版本提供源码下载。原生生成依赖使用者自己电脑上的 Cadence 16.6；网站或 GitHub 项目页只负责介绍、文档和下载，不承担在线转换。

## 真正需要关心的是转换结果

把数据读出来、画出相似的图形，只完成了一部分工作。封装还涉及引脚编号、坐标原点、钻孔、阻焊与锡膏，以及在板顶和板底旋转放置后的行为。某个阶段没有报错，也不代表这些内容都正确。

因此程序把流程拆成几步：

1. 获取或读取源封装，并检查数据身份和支持范围。
2. 建立中间几何模型，记录原点、引脚和焊盘参数。
3. 调用本机 Cadence 16.6 工具生成原生文件。
4. 独立读取生成结果，核对几何、编号、报告和日志。
5. 人工对照图纸与工艺，确认后再放进本地库。

`convert` 成功后还要运行 `verify`。这让“生成出来了”和“经过独立检查了”成为两个可观察的步骤。

## 我选择让一部分输入明确失败

不同封装的数据表达不完全相同。遇到当前没有实现的圆角矩形、自定义焊盘或槽孔，如果直接换成一个看起来差不多的形状，很容易掩盖实际差异。

所以目前的做法是拒绝未支持或含混的输入，并保留失败原因。它意味着工具暂时不能处理所有 C 编号，也意味着使用者能知道边界在哪里。

另外，几何验证不能替代完整制造评审。投板前仍要检查厂家图纸、引脚定义、方向、焊接工艺和装配空间。

## 第一次公开整理做了哪些事

我把源码与本机环境分开：提供配置示例，不上传 Cadence 安装文件、个人历史任务或厂家 PDF；把安装、使用和限制分别写成文档；保留依赖许可；再提供一个不需要 Cadence 就能运行的测试子集。

历史本机集成测试和本次公开包检查也分别记录。这样读者可以区分哪些检查自己下载后就能复现，哪些还需要专用软件与未随包分发的样本。具体结果放在 [验证记录](../validation.md)。

## 从一个小例子开始

安装好环境后，可以先用仓库内的合成排针示例：

```powershell
.\lc2a.ps1 convert --input .\tests\header_1x2.kicad_mod --name DEMO_HEADER_1X2 --refdes J
```

然后把输出的 `job` 路径交给 `verify`。没有安装 Cadence 时，可以加 `--prepare-only` 查看中间结果，但这不会生成已验证的原生封装。

完整步骤见 [安装指南](../installation.md) 和 [使用说明](../usage.md)。

## 接下来

后续可以逐步改进安装体验、增加可公开复现的测试样本，并在有实际输入和验证依据时扩展几何支持。每个新增范围都需要配套测试与原生检查，不把“文件能打开”作为唯一标准。

如果你也在使用 Allegro 16.6，欢迎阅读源码、尝试支持范围内的封装，并通过 [Issues](https://github.com/liuleonmoretti/lcsc-to-allegro/issues) 反馈具体问题。
